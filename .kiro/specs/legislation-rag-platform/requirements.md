# Requirements Document

## Introduction

This document specifies the requirements for the Legislation RAG Platform — a microservices-based implementation that enables internal users to query legislation, policies, and business rules through a natural language chat interface. The platform uses hybrid retrieval (dense vector, sparse BM25, and graph traversal) with Reciprocal Rank Fusion, Strands Agents for orchestration, and a React frontend. The architecture comprises five FastAPI services (API Gateway, Query Service, Ingestion Service, Graph Service, Embedding Service) and a React frontend, deployed via Docker Compose in dev and AWS ECS in prod. Multiple teams collaborate in the dev environment with independent service deployment and shared domain models.

## Glossary

- **Platform**: The Legislation RAG Platform application composed of the React Frontend, API Gateway, Query Service, Ingestion Service, Graph Service, Embedding Service, and supporting infrastructure services
- **Frontend**: The React 19 single-page application providing the chat interface and document management UI, connecting to the API Gateway
- **API_Gateway**: The FastAPI service (dev) or AWS API Gateway (prod) handling routing, rate limiting, authentication, CORS, and correlation ID injection
- **Query_Service**: The FastAPI microservice hosting the RAGOrchestrator and serving /v1/ask and /v1/agents/ask endpoints
- **Ingestion_Service**: The FastAPI microservice handling document upload, chunking, embedding, and graph extraction via /v1/ingest and /v1/documents endpoints
- **Graph_Service**: The FastAPI microservice wrapping Neo4j operations exclusively, exposing entity, relationship, traversal, and deletion endpoints
- **Embedding_Service**: The FastAPI microservice wrapping AWS Bedrock embedding calls with caching and token tracking
- **Orchestrator**: The RAGOrchestrator component within the Query_Service that coordinates the five Strands Agents to process queries
- **Retrieval_Agent**: The Strands Agent responsible for executing hybrid search across dense, sparse, and graph stores via inter-service calls
- **Generation_Agent**: The Strands Agent responsible for producing cited answers from retrieved context
- **Citation_Verification_Agent**: The Strands Agent responsible for verifying that generated citations are supported by source text
- **Ingestion_Agent**: The Strands Agent responsible for processing uploaded documents through the ingestion pipeline
- **Evaluation_Agent**: The Strands Agent responsible for computing confidence scores and determining fallback responses
- **Neo4j_Adapter**: The infrastructure adapter within the Graph_Service implementing GraphStorePort using Neo4j Community Edition with Cypher queries
- **Legal_Hierarchical_Chunker**: The chunking strategy that extends recursive chunking by prepending parent legislative context to each chunk
- **Chunker_Registry**: The component that registers all available chunking strategies and auto-selects based on document format
- **Graph_Store**: The Neo4j Community Edition database storing legal entities and their relationships as a knowledge graph, accessed exclusively through the Graph_Service
- **Vector_Store**: The ChromaDB instance storing document chunk embeddings for dense retrieval
- **Sparse_Index**: The BM25 in-memory index for keyword-based sparse retrieval
- **Reranker**: The cross-encoder model that reranks candidate chunks for final relevance scoring
- **RRF**: Reciprocal Rank Fusion algorithm combining ranked results from dense, sparse, and graph search
- **Confidence_Score**: A composite score calculated as 0.35 x retrieval_confidence + 0.40 x citation_coverage + 0.25 x answer_completeness
- **Fallback_Response**: The response returned when Confidence_Score is below 0.4, indicating insufficient evidence to answer
- **Legal_Entity**: A node in the knowledge graph representing an Act, Section, Regulation, Definition, Obligation, Authority, or Penalty
- **Legal_Relationship**: An edge in the knowledge graph representing CONTAINS, DEFINES, AMENDS, REFERENCES, IMPLEMENTS, IMPOSES, GRANTS_POWER, or PRESCRIBES_PENALTY
- **Golden_Dataset**: A set of 20 question-answer pairs with expected citations used for evaluation
- **Sample_Documents**: A set of 8 synthetic legislative documents styled after transport and road management Acts (Acts, Regulations, policies, business rules) used for development testing
- **Correlation_ID**: A UUID generated by the API_Gateway and propagated via X-Correlation-ID header through all inter-service calls for distributed tracing
- **Circuit_Breaker**: A resilience pattern on inter-service calls that opens after 5 consecutive failures, preventing calls for 30 seconds before attempting reset
- **Service_Discovery**: Docker Compose DNS in dev and AWS Cloud Map in prod for resolving service hostnames
- **Domain_Models_Library**: The shared libs/domain-models/ package containing Pydantic models used across all services
- **OTLP_Exporter**: The OpenTelemetry Protocol exporter sending distributed traces from all services to the observability backend

## Requirements

### Requirement 1: Neo4j Graph Store Adapter

**User Story:** As a developer, I want a Neo4j adapter implementing GraphStorePort, so that legal entities and relationships are stored and traversed in a real graph database instead of the in-memory stub.

#### Acceptance Criteria

1. WHEN the Neo4j_Adapter receives a list of ExtractedEntity objects, THE Neo4j_Adapter SHALL persist each entity as a node in Neo4j with properties: id, name, entity_type, description, source_chunk_id, and all entries from the properties dict, using the entity id as the merge key so that storing an entity with an existing id overwrites the previous node properties
2. WHEN the Neo4j_Adapter receives a list of ExtractedRelationship objects, THE Neo4j_Adapter SHALL persist each relationship as an edge in Neo4j connecting the source_entity_id node to the target_entity_id node with the specified relationship_type and properties, using the relationship id as the merge key so that duplicate relationships are not created
3. IF a relationship references a source_entity_id or target_entity_id that does not exist as a stored node, THEN THE Neo4j_Adapter SHALL skip that relationship and log a warning including the missing entity id
4. WHEN the Neo4j_Adapter receives a traverse query with a max_hops parameter, THE Neo4j_Adapter SHALL execute a Cypher variable-length path traversal up to max_hops hops (capped at a maximum of 5) and return matching nodes whose name or entity_type matches the query text as a list of ScoredChunk objects with score set to 1.0 / (1 + hop_distance) and retrieval_method set to "graph"
5. WHEN the Neo4j_Adapter receives a delete_by_document request with a document_id, THE Neo4j_Adapter SHALL remove all nodes whose source_chunk_id belongs to a chunk with that document_id, and remove all relationships connected to those deleted nodes, within a single transaction
6. IF Neo4j is unavailable or a query exceeds the 5-second timeout during a store or traverse operation, THEN THE Neo4j_Adapter SHALL log the error with structlog including the operation name and document or query context, and raise a GraphStoreUnavailableError that the service layer handles to continue without graph results
7. THE Neo4j_Adapter SHALL use the Neo4j async Python driver with connection pool size between 10 and 50 connections and a per-query timeout of 5 seconds
8. THE Neo4j_Adapter SHALL create indexes on entity_type and source_chunk_id properties during initialization using CREATE INDEX IF NOT EXISTS to ensure idempotent startup
9. WHEN entities are stored via store_entities and then a traverse query matches those entities by name or entity_type, THE Neo4j_Adapter SHALL return ScoredChunk results containing the originally stored entity data including all properties from the properties dict

### Requirement 2: React Frontend Chat Interface

**User Story:** As an internal user, I want a web-based chat interface, so that I can ask natural language questions about legislation and receive cited answers.

#### Acceptance Criteria

1. THE Frontend SHALL render a chat input field that accepts questions up to 1000 characters and allows submission by pressing Enter or clicking a Send button
2. WHEN the user submits a question, THE Frontend SHALL disable the input field to prevent duplicate submissions, send a POST request to the API_Gateway /v1/ask endpoint with the question text, and display a loading indicator until the response arrives or 30 seconds elapse
3. WHEN the API_Gateway returns a successful response, THE Frontend SHALL display the answer text with inline citation markers (e.g., [1], [2]) that link to the corresponding source in the source panel
4. WHEN the API_Gateway returns a response with confidence data, THE Frontend SHALL display the composite confidence score as a color-coded indicator: green for score >= 0.7, amber for score >= 0.4 and below 0.7, and red for score below 0.4
5. WHEN the API_Gateway returns a fallback response (is_fallback is true), THE Frontend SHALL display the fallback information including found topics, not-found topics, and suggested documents
6. THE Frontend SHALL render a source panel listing all retrieved source chunks with their section headings, relevance scores, and retrieval methods
7. WHEN the user clicks a citation marker in the answer, THE Frontend SHALL scroll the source panel to bring the corresponding source chunk into view and visually highlight it
8. THE Frontend SHALL maintain a scrollable conversation history showing all questions and answers from the current browser session, cleared on page reload
9. THE Frontend SHALL be built with React 19, Vite, TypeScript, and TailwindCSS and connect to the API_Gateway at a configurable base URL defaulting to http://localhost:8080
10. IF the user attempts to submit an empty or whitespace-only question, THEN THE Frontend SHALL keep the input field unchanged and not send a request to the API_Gateway
11. IF the API_Gateway request fails due to a network error or the 30-second timeout elapses without a response, THEN THE Frontend SHALL dismiss the loading indicator, re-enable the input field, and display an error message indicating the request failed

### Requirement 3: Document Upload Interface

**User Story:** As an internal user, I want to upload legislative documents through the frontend, so that new legislation and policies are ingested into the platform.

#### Acceptance Criteria

1. THE Frontend SHALL provide a document upload area that accepts files with extensions .txt, .md, .html, and .pdf, with a maximum file size of 50 MB per file, and SHALL reject files with disallowed extensions or exceeding the size limit before sending the request, displaying an inline validation message indicating the reason for rejection
2. WHEN the user selects a valid file for upload, THE Frontend SHALL send a POST request to the API_Gateway at /v1/ingest with the file as multipart form data, and the API_Gateway SHALL proxy the request to the Ingestion_Service, displaying a loading indicator until the response arrives or the request times out
3. WHEN the Ingestion_Service returns a successful ingestion response via the API_Gateway, THE Frontend SHALL display a success notification showing the document filename and chunk count
4. IF the API_Gateway returns an error during ingestion, THEN THE Frontend SHALL display an error notification with the error message from the response
5. WHEN the user navigates to the documents view, THE Frontend SHALL fetch and display a list of all ingested documents from the API_Gateway /v1/documents endpoint (proxied to Ingestion_Service) showing filename, format, and ingestion date, sorted by ingestion date in descending order (most recent first)
6. IF the upload request fails due to a network error or exceeds a 60-second timeout, THEN THE Frontend SHALL display an error notification indicating the upload could not be completed and allow the user to retry the upload without re-selecting the file

### Requirement 4: Legal Domain Agent Customization

**User Story:** As a developer, I want all five Strands Agents configured with legislation-specific system prompts, so that agents understand legal document structure and produce domain-appropriate outputs.

#### Acceptance Criteria

1. THE Retrieval_Agent SHALL use a system prompt that instructs it to recognize legal entity types (Act, Section, Regulation, Definition, Obligation, Authority, Penalty) and to invoke graph traversal as the first retrieval method when the query contains a cross-reference keyword (AMENDS, REFERENCES, IMPLEMENTS, or a specific section number)
2. THE Generation_Agent SHALL use a system prompt that instructs it to produce answers citing specific sections and subsections using the format "[Act/Regulation Title], Section [number]([subsection])", use third-person passive legislative phrasing, and include only claims directly supported by retrieved source chunks
3. THE Citation_Verification_Agent SHALL use a system prompt that instructs it to verify each citation by confirming the quoted text appears verbatim or by paraphrase in the corresponding source chunk, flag any claim not traceable to a source chunk as unsupported, and confirm that cited section numbers match the section_heading metadata of the source chunk
4. THE Ingestion_Agent SHALL use a system prompt that instructs it to extract legal entities (Act, Section, Regulation, Definition, Obligation, Authority, Penalty) and relationships (CONTAINS, DEFINES, AMENDS, REFERENCES, IMPLEMENTS, IMPOSES, GRANTS_POWER, PRESCRIBES_PENALTY) from ingested text, extracting at minimum one entity per legislative section identified in the source
5. THE Evaluation_Agent SHALL use a system prompt that instructs it to assess answer quality by scoring: legislative accuracy as the proportion of legal references that match source text, section-level citation precision as the ratio of citations with verified section numbers to total citations, and completeness of obligation/authority coverage as the ratio of query-relevant obligations and authorities addressed to total obligations and authorities present in retrieved context
6. THE Platform SHALL store each agent's system prompt as a configurable text string loaded at agent initialization, allowing prompt content to be updated without code changes
7. WHEN a query is processed through the Orchestrator, THE Generation_Agent SHALL produce output that contains at least one section-level citation and does not include statements prefaced with speculative language such as "likely", "probably", or "it appears that"
8. IF an agent's system prompt fails to load or is empty at initialization, THEN THE Platform SHALL raise a configuration error and prevent the agent from accepting requests until a valid prompt is provided

### Requirement 5: Legal-Hierarchical Chunker

**User Story:** As a developer, I want a chunking strategy that preserves legislative hierarchy context, so that each chunk contains enough parent context (Act title, Part heading) for standalone comprehension.

#### Acceptance Criteria

1. WHEN the Legal_Hierarchical_Chunker processes a legislative document, THE Legal_Hierarchical_Chunker SHALL prepend the Act title and Part/Division heading to each chunk as contextual prefix separated by a newline character
2. WHEN the Legal_Hierarchical_Chunker processes a document with nested sections, THE Legal_Hierarchical_Chunker SHALL preserve section numbering hierarchy (e.g., "Part 3, Division 2, Section 45") in the chunk metadata under a key named "hierarchy_path"
3. THE Legal_Hierarchical_Chunker SHALL extend the existing recursive chunking strategy, using the same max_chunk_size parameter while adding the hierarchical prefix
4. WHEN the hierarchical prefix plus chunk text exceeds the configured max_chunk_size, THE Legal_Hierarchical_Chunker SHALL prioritize retaining the prefix and reduce the chunk body text rather than truncating the prefix, ensuring the chunk body contains at minimum 100 characters
5. FOR ALL documents chunked by the Legal_Hierarchical_Chunker, every output chunk SHALL contain a non-empty section_heading field and a metadata entry identifying the parent Act or Regulation title under the key "parent_document_title"
6. IF a document does not contain identifiable Act or Regulation title markers, THEN THE Legal_Hierarchical_Chunker SHALL use the document filename as the parent_document_title and log a warning

### Requirement 6: Chunker Registry and Auto-Selection

**User Story:** As a developer, I want all chunking strategies registered and auto-selected based on document format, so that each document type receives the most appropriate chunking treatment.

#### Acceptance Criteria

1. THE Chunker_Registry SHALL register the fixed-size, recursive, semantic, and legal-hierarchical chunking strategies during the application lifespan event before any ingestion requests are accepted
2. WHEN a document is ingested without an explicit chunking strategy, THE Chunker_Registry SHALL determine the document format from the file extension (.pdf, .md, .html, .txt) and auto-select the strategy: legal-hierarchical for .pdf and .md files whose filename or metadata contains a legislative keyword (Act, Regulation, Rule, Policy), recursive for .html files, and fixed-size for .txt files
3. IF the auto-selected strategy is unavailable because it failed to initialize or its required dependencies are not reachable, THEN THE Chunker_Registry SHALL fall back to the fixed-size chunking strategy and log a warning that includes the originally selected strategy name and the reason for unavailability
4. THE Chunker_Registry SHALL expose a list of all registered strategies via the registered_strategies property, returning strategy name and availability status for each entry
5. WHEN a document is ingested with a file extension not in the set (.pdf, .md, .html, .txt), THE Chunker_Registry SHALL default to the fixed-size chunking strategy
6. WHEN a document is ingested with an explicit chunking strategy name that matches a registered strategy, THE Chunker_Registry SHALL use the specified strategy instead of auto-selection
7. IF a document is ingested with an explicit chunking strategy name that does not match any registered strategy, THEN THE Chunker_Registry SHALL reject the request and return an error indicating the strategy name is not recognized

### Requirement 7: Orchestrator-API Integration

**User Story:** As a developer, I want the RAGOrchestrator wired into the Query_Service /v1/agents/ask endpoint, so that queries are processed through the full agent pipeline with inter-service calls to the Graph_Service and Embedding_Service.

#### Acceptance Criteria

1. WHEN the Query_Service receives a POST request to /v1/agents/ask with a JSON body containing a non-empty query string (maximum 2000 characters), THE Query_Service SHALL route the query through the Orchestrator which coordinates the Retrieval_Agent, Generation_Agent, Citation_Verification_Agent, and Evaluation_Agent in sequence, making HTTP calls to the Graph_Service for traversal and the Embedding_Service for vector generation, and return an HTTP 200 response within 30 seconds
2. THE Query_Service SHALL inject the Orchestrator as a dependency using FastAPI Depends, with the Orchestrator created during the application lifespan event and stored in app.state
3. WHEN the Orchestrator completes processing, THE Query_Service SHALL return a JSON response containing: answer (string), citations (array of objects each with source reference and verification status), confidence_scores (object with retrieval_confidence, citation_coverage, answer_completeness, and composite fields), source_chunks (array of retrieved chunk objects), and is_fallback (boolean)
4. IF any agent in the Orchestrator pipeline raises an exception or an inter-service call to Graph_Service or Embedding_Service fails after retries, THEN THE Query_Service SHALL return an HTTP 500 response with a JSON body containing error_code (string identifying the failing agent or service), message (string describing the failure), and correlation_id (string matching the X-Correlation-ID header from the API_Gateway)
5. THE Query_Service SHALL retain the existing /v1/ask endpoint for direct retrieval-only queries while the /v1/agents/ask endpoint provides the full agent-orchestrated pipeline
6. IF the POST request to /v1/agents/ask contains a missing or empty query field or exceeds 2000 characters, THEN THE Query_Service SHALL return an HTTP 422 response with a JSON body containing an error message indicating the validation failure
7. WHEN the Orchestrator returns a generated answer to the Query_Service, THE Query_Service SHALL sanitize the output by stripping any HTML tags, JavaScript code, and control characters from the answer text before including it in the API response, ensuring no executable content is returned to the client

### Requirement 8: Sample Legislative Data

**User Story:** As a developer, I want synthetic legislative documents and a golden Q&A dataset, so that I can test and evaluate the platform without real legislative data.

#### Acceptance Criteria

1. THE Sample_Documents SHALL include 8 synthetic documents: 2 Acts (modeled on Transport Infrastructure Act and Road Use Management Act structure), 2 Regulations (driver licensing, heavy vehicle access), 2 internal policies, and 2 business rules documents
2. THE Sample_Documents SHALL contain legislative structure including at minimum 2 Parts, 2 Divisions, and 5 Sections per Act document, with at least 4 cross-references between different documents, at least 2 definitions sections, and at least 2 penalty provisions
3. THE Golden_Dataset SHALL contain 20 question-answer pairs covering: licence queries (5), permit/route queries (5), legislative interpretation (5), and road design standards (5), where every expected answer is fully derivable from the content of the Sample_Documents
4. EACH entry in the Golden_Dataset SHALL include: the question text (maximum 300 characters), the expected answer (maximum 2000 characters), the expected source document filename and section references, and the minimum acceptable confidence score expressed as a decimal value between 0.0 and 1.0
5. THE Sample_Documents SHALL exercise all defined legal entity types (Act, Section, Regulation, Definition, Obligation, Authority, Penalty) and relationship types (CONTAINS, DEFINES, AMENDS, REFERENCES, IMPLEMENTS, IMPOSES, GRANTS_POWER, PRESCRIBES_PENALTY) with at least one instance of each entity type and one instance of each relationship type
6. THE Sample_Documents SHALL be provided in Markdown format with each document containing a minimum of 1500 characters of body text to ensure sufficient content for chunking and retrieval testing
7. IF the Golden_Dataset references a source document or section that does not exist in the Sample_Documents, THEN THE evaluation SHALL treat this as a dataset validation failure

### Requirement 9: End-to-End Testing

**User Story:** As a developer, I want automated E2E tests covering the complete ingest-to-query pipeline across service boundaries, so that I can verify the microservices system works correctly as an integrated whole.

#### Acceptance Criteria

1. THE Platform SHALL include E2E tests that send an ingest request through the API_Gateway to the Ingestion_Service for a sample document, then send a query through the API_Gateway to the Query_Service, and verify the response includes at least one citation whose source_chunk_id references a chunk from the ingested document and whose verification status is "verified"
2. THE Platform SHALL include E2E tests that verify graph traversal across service boundaries: the Query_Service calls the Graph_Service via HTTP, and the Graph_Service returns at least one related entity when querying for a section that has an AMENDS or REFERENCES relationship to another section in the ingested Sample_Documents
3. THE Platform SHALL include E2E tests that verify fallback behavior: when a query has no relevant documents ingested, the response is_fallback flag is true, confidence composite is below 0.4, and the response includes a non-empty suggested_documents list
4. THE Platform SHALL include E2E tests for the React Frontend using Playwright that verify: submitting a question displays a non-empty answer within 30 seconds, at least one citation marker is rendered and clickable, and the source panel renders at least one source chunk with a visible section heading
5. WHEN an E2E test fails, THE test output SHALL include the correlation_id from the X-Correlation-ID response header to enable distributed log correlation for debugging across services
6. THE Platform SHALL execute each individual E2E test within a maximum timeout of 60 seconds, failing the test with a timeout error if the duration is exceeded
7. THE Platform SHALL include E2E tests that verify inter-service circuit breaker behavior: when the Graph_Service is unavailable, the Query_Service returns a degraded response using only dense and sparse search within the 30-second timeout

### Requirement 10: Hybrid Search with Graph Integration

**User Story:** As an internal user, I want searches to combine vector similarity, keyword matching, and legislative graph traversal via inter-service calls, so that queries about cross-referenced legislation return comprehensive and contextually connected results.

#### Acceptance Criteria

1. WHEN a query is submitted, THE Retrieval_Agent in the Query_Service SHALL execute dense search (ChromaDB vector similarity using embeddings from the Embedding_Service via HTTP), sparse search (BM25 keyword matching), and graph search (Neo4j traversal via HTTP call to the Graph_Service) in parallel, with each method subject to an individual timeout of 5 seconds before being declared unavailable
2. THE Retrieval_Agent SHALL retrieve the top 20 candidates from each search method and fuse them using Reciprocal Rank Fusion with default weights: dense=0.5, sparse=0.2, graph=0.3
3. WHEN a query contains an explicit legislative section reference (e.g., "Section 45", "s.12", "Part 3 Division 2") that has AMENDS or REFERENCES relationships in the graph, THE Graph_Service SHALL return the related sections via traversal up to 2 hops
4. IF one or two search methods are unavailable (timeout exceeded or downstream service unreachable), THEN THE Retrieval_Agent SHALL renormalize the RRF weights proportionally across the remaining available methods, fuse results from those methods, and log the degradation including which methods and services were unavailable
5. THE Reranker SHALL rerank the top 20 fused candidates using the cross-encoder model and return the top 5 results to the Generation_Agent; IF fewer than 20 candidates are available after fusion, THEN THE Reranker SHALL rerank all available candidates and return up to 5 results

### Requirement 11: Confidence Scoring and Fallback

**User Story:** As an internal user, I want to see a confidence score on every answer and receive a clear fallback when evidence is insufficient, so that I know when to trust the answer and when to consult legislation directly.

#### Acceptance Criteria

1. THE Evaluation_Agent SHALL compute a composite confidence score using the formula: composite = 0.35 x retrieval_confidence + 0.40 x citation_coverage + 0.25 x answer_completeness, where each sub-score is a decimal value in the range [0.0, 1.0] and the composite result is rounded to two decimal places
2. WHEN the composite confidence score is below 0.4, THE Platform SHALL return a Fallback_Response that states it cannot provide a confident answer, lists the topics for which partial information was found, lists the topics for which no information was found, and suggests up to 3 documents from the retrieved sources ranked by relevance score for manual consultation
3. WHEN the composite confidence score is 0.4 or above, THE Platform SHALL return the generated answer with all citations and the confidence breakdown (retrieval_confidence, citation_coverage, answer_completeness, composite) as numeric values rounded to two decimal places
4. THE Evaluation_Agent SHALL compute retrieval_confidence as the maximum reranked score among retrieved chunks normalized to [0.0, 1.0], citation_coverage as the number of answer statements that have at least one verified citation divided by the total number of distinct factual statements in the answer, and answer_completeness as the number of distinct entities or concepts from the user query that are addressed in the answer divided by the total number of distinct entities or concepts identified in the user query
5. IF no chunks are retrieved or the Reranker returns zero results, THEN THE Evaluation_Agent SHALL set retrieval_confidence to 0.0, citation_coverage to 0.0, and answer_completeness to 0.0, resulting in a composite score of 0.0 and triggering the Fallback_Response

### Requirement 12: API Gateway Service

**User Story:** As a developer, I want a centralized API Gateway that handles routing, authentication, rate limiting, and correlation ID injection, so that downstream services are decoupled from cross-cutting concerns and all requests are traceable.

#### Acceptance Criteria

1. THE API_Gateway SHALL authenticate every incoming request by validating an API key provided in the X-API-Key header against a configured set of valid keys, returning HTTP 401 with an error message if the key is missing or invalid
2. THE API_Gateway SHALL enforce rate limiting of 60 requests per minute per API key in the dev environment using in-memory token bucket storage; WHILE in the prod environment, THE API_Gateway SHALL delegate rate limiting to AWS API Gateway throttling configuration
3. WHEN a request arrives, THE API_Gateway SHALL generate a UUID v4 Correlation_ID and inject it as the X-Correlation-ID header on the proxied request to downstream services, and include the same X-Correlation-ID in the response headers to the client
4. THE API_Gateway SHALL configure CORS to allow origins http://localhost:3000 and http://localhost:5173 in the dev environment with methods GET, POST, DELETE and headers Content-Type, X-API-Key, X-Correlation-ID
5. THE API_Gateway SHALL route requests with path prefix /v1/ask and /v1/agents/ask to the Query_Service, and requests with path prefix /v1/ingest and /v1/documents to the Ingestion_Service, using Docker Compose DNS for service resolution in dev and AWS Cloud Map in prod
6. THE API_Gateway SHALL apply a proxy timeout of 30 seconds for /v1/ask and /v1/agents/ask requests and 60 seconds for /v1/ingest requests, returning HTTP 504 with a JSON error body if the timeout is exceeded
7. THE API_Gateway SHALL expose an aggregated /health endpoint that checks connectivity to all downstream services (Query_Service, Ingestion_Service, Graph_Service, Embedding_Service) and returns HTTP 200 with individual service statuses when all are healthy, or HTTP 503 with the failing service names when any downstream service is unreachable
8. THE API_Gateway SHALL log every request and response with structlog in JSON format including: method, path, status_code, duration_ms, correlation_id, and API key identifier (not the full key value)
9. THE API_Gateway SHALL include security headers on all responses using the secure library including: Strict-Transport-Security (max-age=31536000), X-Frame-Options (DENY), X-Content-Type-Options (nosniff), Referrer-Policy (no-referrer), and X-XSS-Protection (1; mode=block)
10. THE API_Gateway SHALL integrate fastapi-guard middleware for automated penetration attempt detection including SQL injection patterns, XSS payloads, path traversal sequences, and command injection patterns in request paths, query parameters, and headers, returning HTTP 403 with a JSON error body when a malicious pattern is detected

### Requirement 13: Inter-Service Communication

**User Story:** As a developer, I want resilient inter-service communication with circuit breakers, retries, and correlation ID propagation, so that partial failures do not cascade and all requests remain traceable across service boundaries.

#### Acceptance Criteria

1. THE Platform SHALL implement all service-to-service HTTP calls using httpx AsyncClient with connection pooling (max_connections=100, max_keepalive_connections=20) shared per service instance
2. WHEN a service makes an inter-service call, THE calling service SHALL propagate the X-Correlation-ID header received from the upstream request to all downstream HTTP calls
3. THE Platform SHALL implement a Circuit_Breaker on every inter-service call that transitions to the open state after 5 consecutive failures, rejects all calls for 30 seconds in the open state, then transitions to half-open allowing a single probe request to determine recovery
4. WHEN an inter-service call fails, THE calling service SHALL retry with exponential backoff using a base delay of 1 second, a multiplier of 2, and a maximum of 3 attempts, applying jitter of up to 500 milliseconds to each delay
5. WHEN the Circuit_Breaker is in the open state for a non-critical service (Graph_Service, Embedding_Service), THE calling service SHALL return a degraded response using available data from other methods rather than failing the entire request
6. IF the Circuit_Breaker is in the open state for a critical service dependency that has no fallback, THEN THE calling service SHALL return HTTP 503 with a JSON body containing the service name and estimated recovery time
7. THE Platform SHALL implement readiness probes (/health/ready) on each service that verify connectivity to the service's required dependencies (database, external APIs), returning HTTP 200 when ready and HTTP 503 when not ready

### Requirement 14: Graph Service

**User Story:** As a developer, I want a dedicated Graph Service that owns all Neo4j operations, so that no other service connects to Neo4j directly and graph concerns are isolated behind a clear API boundary.

#### Acceptance Criteria

1. THE Graph_Service SHALL be a standalone FastAPI application exposing endpoints: POST /entities (batch store entities), POST /relationships (batch store relationships), POST /traverse (execute graph traversal query), and DELETE /documents/{document_id} (delete all entities and relationships for a document)
2. THE Graph_Service SHALL own the Neo4j connection exclusively; no other service in the Platform SHALL connect to Neo4j directly
3. WHEN the Graph_Service receives a POST /entities request with a list of entity objects, THE Graph_Service SHALL validate the request body against the shared ExtractedEntity Pydantic model from the Domain_Models_Library and persist entities using the Neo4j_Adapter
4. WHEN the Graph_Service receives a POST /traverse request with a query string and max_hops parameter, THE Graph_Service SHALL execute the traversal via the Neo4j_Adapter and return a JSON response containing the list of ScoredChunk results
5. THE Graph_Service SHALL expose /health checking Neo4j connectivity, /health/ready verifying the Neo4j connection pool is established and indexes exist, and /health/live returning HTTP 200 if the process is running
6. IF the Graph_Service receives a request with an invalid or malformed body, THEN THE Graph_Service SHALL return HTTP 422 with a JSON error detailing the validation failures
7. THE Graph_Service SHALL accept and log the X-Correlation-ID header from incoming requests and include it in all structured log entries

### Requirement 15: Embedding Service

**User Story:** As a developer, I want a dedicated Embedding Service that wraps Bedrock embedding calls with caching and token tracking, so that embedding operations are centralized, redundant API calls are avoided, and costs are tracked.

#### Acceptance Criteria

1. THE Embedding_Service SHALL be a standalone FastAPI application exposing endpoints: POST /embed (single text input returning a vector) and POST /embed/batch (list of text inputs returning a list of vectors)
2. WHEN the Embedding_Service receives a POST /embed request with a text string, THE Embedding_Service SHALL compute a SHA-256 hash of the text, check the embedding cache for a matching hash, and return the cached vector if found without calling Bedrock
3. IF the embedding cache does not contain a matching hash, THEN THE Embedding_Service SHALL call AWS Bedrock to generate the embedding, store the result in the cache keyed by the text hash, and return the vector in the response
4. WHEN the Embedding_Service receives a POST /embed/batch request with a list of texts, THE Embedding_Service SHALL check the cache for each text individually, call Bedrock only for uncached texts, cache the new results, and return all vectors in the original list order
5. THE Embedding_Service SHALL track token usage per request and return the token count in the response body under a field named "tokens_used"
6. THE Embedding_Service SHALL expose /health checking Bedrock connectivity by making a lightweight API call, /health/ready verifying the cache is initialized and Bedrock credentials are valid, and /health/live returning HTTP 200 if the process is running
7. IF Bedrock is unavailable or returns an error, THEN THE Embedding_Service SHALL return HTTP 503 with a JSON body containing the error description and the X-Correlation-ID from the request
8. THE Embedding_Service SHALL accept and log the X-Correlation-ID header from incoming requests and include it in all structured log entries
9. WHEN the Embedding_Service receives an embed or embed/batch request, THE Embedding_Service SHALL estimate the token count of each input text before calling Bedrock, and IF the estimated token count exceeds the model's maximum input limit of 8192 tokens, THEN THE Embedding_Service SHALL reject that text with an HTTP 422 response indicating the text exceeds the token budget rather than sending an oversized request to Bedrock

### Requirement 16: Service Infrastructure

**User Story:** As a developer, I want each microservice to follow a consistent project structure with independent builds, shared domain models, and Docker Compose orchestration, so that teams can develop and deploy services independently.

#### Acceptance Criteria

1. EACH service (API_Gateway, Query_Service, Ingestion_Service, Graph_Service, Embedding_Service) SHALL have its own directory containing: a Dockerfile, a pyproject.toml, a tests/ directory, and a src/ directory with its own FastAPI application entry point
2. THE Platform SHALL maintain a shared libs/domain-models/ package containing Pydantic models (ExtractedEntity, ExtractedRelationship, ScoredChunk, QueryRequest, QueryResponse, IngestionRequest, IngestionResponse) used across multiple services, installed as an editable package in dev via pip install -e
3. THE Platform SHALL provide a docker-compose.yml that defines all services with health checks, dependency ordering (Graph_Service and Embedding_Service start before Query_Service and Ingestion_Service, all backend services start before API_Gateway), and a shared network for DNS-based service discovery
4. EACH service SHALL expose three health endpoints: /health (basic liveness), /health/ready (readiness with dependency checks), and /health/live (process liveness returning HTTP 200 unconditionally)
5. THE Platform SHALL use structlog configured in JSON format across all services with consistent fields: timestamp, level, service_name, correlation_id, and message
6. EACH service's Dockerfile SHALL use a multi-stage build with a builder stage for installing dependencies and a runtime stage based on python:3.11-slim, producing images under 500 MB

### Requirement 17: SSDLC and Security Governance

**User Story:** As a security engineer, I want threat modeling, static analysis, dependency scanning, and defense-in-depth validation built into the platform, so that security vulnerabilities are identified early and mitigated systematically.

#### Acceptance Criteria

1. THE Platform SHALL maintain a documented STRIDE threat model covering the RAG pipeline data flow from ingestion through retrieval to generation, identifying threats for each service boundary and data store interaction
2. THE Platform SHALL run SAST scanning using bandit for Python services and eslint-plugin-security for the React Frontend as part of the CI pipeline, failing the build if any high-severity finding is detected
3. THE Platform SHALL run dependency scanning using pip-audit for Python services and npm audit for the Frontend as part of the CI pipeline, failing the build if any critical vulnerability is detected in a direct dependency
4. THE Platform SHALL manage secrets using environment variables in the dev environment and AWS Secrets Manager in the prod environment; no secret values SHALL be committed to version control or appear in log output
5. THE Platform SHALL perform input validation at the API_Gateway boundary AND at each individual service boundary (defense in depth), ensuring that malformed or oversized payloads are rejected before reaching business logic
6. THE API_Gateway SHALL include Content-Security-Policy headers on responses served to the Frontend, restricting script sources to self and inline scripts required by the application framework
7. THE Platform SHALL implement PII detection on all structured log output, ensuring that raw user query text is truncated to 100 characters in logs, API key values are never logged in full (only first 8 characters), and no personally identifiable information (email addresses, names from document content) appears in log entries or error responses returned to clients

### Requirement 18: Observability Framework

**User Story:** As a DevOps engineer, I want distributed tracing, metrics, and alerting across all services, so that I can monitor system health, diagnose latency issues, and track costs in the multi-service architecture.

#### Acceptance Criteria

1. THE Platform SHALL instrument all services with OpenTelemetry distributed tracing, exporting spans via the OTLP_Exporter to a configured collector endpoint, with each span containing service_name, correlation_id, operation_name, and duration_ms
2. EACH service SHALL expose Prometheus-compatible metrics at a /metrics endpoint including: request_latency_seconds (histogram), request_total (counter by status_code), active_requests (gauge), and error_total (counter by error_type)
3. THE Platform SHALL provide Grafana dashboard configurations for: a system overview showing all services, a per-service detail view, and an agent pipeline view showing latency breakdown across Retrieval_Agent, Generation_Agent, Citation_Verification_Agent, and Evaluation_Agent stages
4. THE Platform SHALL define alerting rules that trigger when: P99 latency exceeds 30 seconds for any service, error rate exceeds 5 percent over a 5-minute window for any service, or any service health check fails for more than 60 consecutive seconds
5. THE Platform SHALL track and expose token usage metrics per agent per request, enabling cost attribution by aggregating Bedrock API token consumption through the Embedding_Service token tracking
6. WHEN a distributed trace spans multiple services, THE OTLP_Exporter SHALL correlate spans using the X-Correlation-ID as the trace parent identifier, enabling end-to-end latency visualization from API_Gateway through to Graph_Service and Embedding_Service

### Requirement 19: CI/CD Pipeline

**User Story:** As a developer, I want per-service CI pipelines with test gates, contract tests, and security scanning, so that each service can be independently validated and deployed with confidence.

#### Acceptance Criteria

1. EACH service SHALL have its own CI pipeline that executes the following stages in order: lint (ruff for Python, eslint for Frontend), typecheck (mypy for Python, tsc for Frontend), unit tests, property-based tests, integration tests, security scan (bandit/pip-audit for Python, eslint-plugin-security/npm audit for Frontend), and Docker image build
2. THE Platform SHALL maintain shared pipeline templates in a .gitlab-ci/ directory that individual service pipelines extend, reducing duplication across service CI configurations
3. THE CI pipeline SHALL enforce test gates requiring: minimum 80 percent code coverage for unit and property tests combined, all property-based tests passing, and no critical or high vulnerabilities detected by security scanning tools
4. THE Platform SHALL include contract tests that verify API schemas between services match: the Query_Service client expectations match the Graph_Service and Embedding_Service response schemas, and the API_Gateway routing matches downstream service endpoint definitions
5. THE CI pipeline SHALL include a Postman/Newman API test stage that executes a collection of integration tests against a Docker Compose environment with all services running, verifying end-to-end request flows through the API_Gateway
6. WHEN a CI pipeline fails at any stage, THE pipeline SHALL report the failing stage, specific test or check that failed, and the correlation_id of any failed API requests to enable debugging
7. THE CI pipeline SHALL build and tag Docker images for each service using the git commit SHA as the image tag, pushing images to the container registry only when all preceding stages pass
